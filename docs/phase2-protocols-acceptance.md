# 阶段 2：其余选定协议收口验收

日期：2026-10-16（Asia/Shanghai）。版本：`0.7.0a1`。沿用专用 Debian 12 amd64 VPS，sing-box 1.14.3、Mihomo 1.19.32、Nginx 1.30.5、Node 24.21.0 均未升级。**总方案第 6 节明确支持的本机协议范围通过，阶段 2 据此收口；完整首版仍未完成。** Trojan H2 明确拒绝，H2 UDP 未纳入锁定 Mihomo 支持范围，外部 URI 导入与独立 Direct 转发没有实现。公网 IPv6、指定 GUI 及正式发行资源门槛仍未验证；同日审批发现常驻 RSS 与既定目标的差距，见文末复核。

## 交付

新增最多 32 个受管独立节点，覆盖 VLESS、VMess、Trojan、Shadowsocks、TUIC v5、AnyTLS、SOCKS5。稳定 ID、独立 IPv4 监听和随机凭据均由模型校验；名称、传输、端口更新及启停不换凭据。删除须先停用，停用仍保留端口、证书与 REALITY 目标依赖。CLI `proxyhub proxy node` 与面板共用类型化计划，普通资源、预览和任务结果不返回凭据。

每个节点使用 `proxyhub-node@<id>.service`，只读取 `nodes/<id>.json`。证书 PEM 内嵌于 `0640 root:proxyhub-proxy` 不可变运行配置，证书归档 `0700` 与私钥 `0600` 不放宽。激活只调整变化实例与订阅发布，恢复先校验候选 manifest 与类型化差异；恢复失败保留 journal。证书指纹取自本次运行配置中的叶证书，普通 PKI/名称验证与叶指纹验证分别执行。

唯一转换器追加启用节点，保留原 REALITY/HY2 排序、默认选择、用户覆盖和元数据。Mihomo YAML 与通用 URI 同源，供运行健康检查使用的 JSON proxies 也来自同一转换器，不新增第二个客户端渲染器。

## 发现与明确边界

- **Trojan H2**：锁定 Mihomo 的 Trojan transport 分支没有 H2，填写 H2 会落到默认 TCP。本产品在模型、转换器和面板明确拒绝，未将来源项目的 H2 声明记为已实现。依据：[锁定 Trojan 实现](https://github.com/MetaCubeX/mihomo/blob/v1.19.32/adapter/outbound/trojan.go)。
- **H2 UDP**：VLESS TLS H2 的 Mihomo UDP 连续失败，换 packetaddr 仍失败；同一服务端、同一 H2/XUDP 配置使用锁定 sing-box 客户端时 TCP/UDP 通过。H2 的 Mihomo YAML 因此声明 `udp:false`，仅承诺 TCP。锁定 [H2 连接实现](https://github.com/MetaCubeX/mihomo/blob/v1.19.32/transport/vmess/h2.go)的首次读写初始化缺少显式同步是可能原因，未被证明为根因；没有修改或升级锁定核心。
- **UDP 默认 DIRECT**：`udp:false` 下曾观察到的本机回显成功来自规则跳过后的 DIRECT，不能算 H2 成功。使用不存在的 SOCKS5 代理进行对照，无拒绝尾规则时回显成功，加 `MATCH,REJECT` 后拒绝，已真实复现。生成器只在额外节点含 `udp:false` 时增加该尾规则，原 REALITY/HY2 输出规则保留；显式 global/direct 模式不使用此 rule 边界。依据：[规则匹配](https://github.com/MetaCubeX/mihomo/blob/v1.19.32/tunnel/tunnel.go)、[选择组 UDP 能力](https://github.com/MetaCubeX/mihomo/blob/v1.19.32/adapter/outboundgroup/selector.go)。
- **TUIC ALPN**：原服务虽启动，真实客户端报 `CRYPTO_ERROR 0x178: server did not select an ALPN protocol`；仅增加服务端 `tls.alpn:[h3]` 后 TCP/UDP 均通过。锁定 [TUIC 服务](https://github.com/SagerNet/sing-quic/blob/75c3ac4fa12b/tuic/service.go)不补默认 ALPN，而 [HY2 服务](https://github.com/SagerNet/sing-quic/blob/75c3ac4fa12b/hysteria2/service.go)会补 h3，已据此修正渲染。
- **立即重新启用**：真实面板暴露 TCP TIME_WAIT 被端口预检误认为占用。Linux 回归先证明普通 bind 被 TIME_WAIT 拒绝，随后验证与监听一致的 `SO_REUSEADDR` 策略可用，并仍拒绝真正 LISTEN 的套接字。修复后面板立即停启循环通过。
- **原始 URI**：HTTPUpgrade、Trojan WS Host、SOCKS UDP 开关及 H2 UDP 声明不能由锁定 Mihomo 原始 URI 导入器无损恢复。通用分享 URI 保留协议参数，完整交付基准为 Mihomo YAML；没有声称 raw 重新导入逐组合通过。详见[转换器说明](../packages/converter/README.md)与[锁定 URI 导入器](https://github.com/MetaCubeX/mihomo/blob/v1.19.32/common/convert/converter.go)。

## 2026-10-16 资源前置评估

本节为上述审批后的专项评估，基线提交及运行时未变。**评估完成，资源调整尚未实施，线上仍是 10 个代理核心进程；原 RSS <350 MiB、刷新峰值 <650 MiB、无 OOM 的门槛不变。** 以下分清线上观察、隔离实测和预算估算，不把它们当作正式 1 核 1GB、5 订阅/500 节点验收。

### 复现与原因

11:54:56（Asia/Shanghai），通过 SSH stdin 执行 `python3 -`，枚举 active 的 `proxyhub-*` 服务 cgroup，读取全部进程 `smaps_rollup`，以 `sum(Rss) < 350 * 1024 KiB` 为判定。结果为 14 项服务、15 个进程、RSS 790,744 KiB（772.2 MiB），判定 false、退出码 1；与 11:44 的观察一致。未停止任何现有进程来缩小样本，而是按服务与映射分类定位开销。

11:57 的 `/proc/<pid>/smaps` 分类结果如下；同一物理共享页仍按原 RSS 口径在各进程中计数。

| 对象 | RSS 合计 | 发现 |
| --- | ---: | --- |
| 10 个核心的程序文件映射 | 475.1 MiB | 都是同一 device/inode、同一 81,338,597-byte 官方程序；每进程约 45.8–48.9 MiB，并非十份不同二进制 |
| 10 个核心的匿名映射 | 178.4 MiB | 每进程约 16.3–20.2 MiB；包含运行时、堆等，不能全称为泄漏或可回收堆 |
| 10 个核心的其他文件映射 | 11.0 MiB | 其余映射开销 |
| manager、panel、publisher、Nginx | 107.7 MiB | 其中 panel 约 45.2、manager 23.4、publisher 21.9、Nginx 两进程 17.2 MiB |
| 全部相关进程 | 772.2 MiB | 核心共 664.5 MiB，是主要调整对象 |

排序验证的假设及结论：

1. **每节点独立核心重复驻留程序与运行时：成立，是主因。** 程序映射本身已超过 350 MiB；隔离合并实验进一步验证多入站共用进程只需驻留一份程序。代码位置为 `installer.units()` 的四类核心 unit、`nodes.render_node()` 和 `deployment._sync_nodes()`，当前确实按节点独立启动。
2. **验收后堆膨胀是主因：证据不支持。** 匿名映射不是最大项；即使假设十个核心的全部匿名映射消失，程序/其他文件映射加其余服务仍约 593.8 MiB。短窗口稳定不等于排除长期泄漏，本任务无需为解释当前超标增加堆转储或常驻 profiler。
3. **遗留客户端/转换器或异常线程数：未发现。** 10 个 sing-box 均属于上述服务，每核心 9–10 个线程，服务重启计数为 0；检查时没有 Mihomo/Node 测试进程。另有 3 个常驻 Python 服务和本次短时采样 Python。
4. **单一协议异常：未见主要证据。** 各核心 RSS 为约 63.1–68.9 MiB；合并后认证各协议只增加少量内存。透明大页是次要观察因素：主机 THP 为 `always`，线上核心的 `AnonHugePages` 为 14–18 MiB，但不改变程序映射重复计入 RSS 的主因。

`GOMEMLIMIT` 约束的是 Go 运行时管理的内存，明确不包含 Go 程序二进制；不能据此承诺总 RSS 上限，见 [Go SetMemoryLimit 文档](https://pkg.go.dev/runtime/debug#SetMemoryLimit)。因此本次没有设置全局 sysctl、清缓存、强制 GC、增加 Swap，或通过 cgroup/PSS 换口径声称达标。

### 隔离对照与方案选择

### 最小调整方案与验收约束

1. 保留两个 REALITY 服务及其现有 SNI/监听映射，保留 Nginx、manager/panel/publisher 的结构。HY2 和现有七类额外节点改由一个固定共享运行组承载；保留全部稳定 ID、名称、端口、密码/UUID、证书、客户端条目、订阅令牌和 URL，不以删除验收节点或退役旧入口减少 RSS。
2. 复用 `hy2.render_hy2()`、`nodes.render_node()`、候选 manifest、revision/journal 与原生成器，仅在运行配置汇总和服务激活边界增加共享组处理。各入站 tag 必须唯一；SOCKS 关闭 UDP 时现有全局 reject 规则须限定到对应入站，避免阻断同组 HY2/其他节点。资源启停状态按资源与组配置判断，不能由组进程 active 推断某个已停用节点仍在提供服务。
3. 节点/证书变化仅在组运行配置实际变化时重启共享组；元数据/名称等未改变运行配置的更新仍只发布。**代价是组内更新、证书重载和故障会共同影响 HY2 及七类节点的连接。** 预览明确列出全部受影响入站，健康检查覆盖组内全部启用成员；不能沿用“只重启变化节点、其余代理连接不变”的旧结论。两个独立 REALITY、网站和订阅应持续可用。
4. 迁移使用一笔可恢复事务：候选校验和隔离认证 → 保存旧 unit/配置及期望服务集合 → 停止被合并的旧实例 → 启动共享组并验证 → 确认发布与提交。迁移期间同端口不能被新旧组同时占用；HY2/额外节点会有短暂重连，不承诺无缝迁移。失败或进程中断须先停止候选组，再恢复旧实例及发布；恢复失败保留 journal。禁止先删旧配置、在成功前永久停用回退路径。
5. 实施预算暂定现有负载总 RSS **≤325 MiB**，为阶段 3 新增常驻开销预留 **20 MiB**，合计预算 ≤345 MiB；这是比原指标更保守的工作预算，不是已通过的测量。若超预算，先重新评估，不放宽 RSS <350 MiB。刷新/候选检查/Mihomo 健康探针/转换器等瞬态进程均计入峰值，串行执行重任务；原峰值 <650 MiB 与无 OOM 条件不变。
6. 只补测改变的边界：组配置与入站规则隔离、启停/证书变更的影响列表、组内各协议真实 TCP/UDP、候选失败及真实中断回滚、原/新 REALITY 长连接和网站/订阅保持、常驻与变更峰值。既有未改的协议组合不重复全量运行。随后 3a 先测 5 份订阅，3b 外部节点导入具备后补足总计 500 个节点，检查生成、刷新与覆盖；不能用当前少量本机节点替代该负载。3d 验证计量构建及采集增量，正式 1 核 1GB 全负载仍归 PERF-1。

收尾检查确认 14 项线上服务的 PID、current 指向、正式配置及发布 bundle 摘要均保持，两个网站的 TLS/正文、两条 REALITY 的 SNI 网站路径及认证代理请求、HY2 认证请求正常；公网 443 监听上的 YAML/raw GET/HEAD 共四项验证通过。最终 12:11:41 检查临时资源目录与健康探针目录均为 0。HEAD 验证脚本曾因遗漏请求方法而误读响应体，修正脚本后仅补测 GET/HEAD，不计为应用故障。此处检查从验收机发起，不冒充个人电脑的外网复验。

**后续顺序调整为：资源评估完成 → 上述共享运行组调整及资源/恢复验收 → 3a 多订阅与安全链接 → 3b 外部源 → 3c 规则与配置编辑 → 3d 共享计量。** 本任务按要求止于诊断、隔离验证和方案维护；没有部署共享组，所以原线上 RSS 检查仍未达标，PERF-1 与资源调整不能标记通过。
